# 봇 공통 합류 절차 — DL-20261110-01

정책: [업무 위임 루프 사칙](../../../principles/delegation-loop.md)
상태: 절차 채택 / 실제 봇별 적용·왕복 확인 미실시

## 1. 수신과 신원 확인

사용자의 공통 메시지를 받으면 캠페인 ID, 수신 시각, 실제 읽은 규칙 commit, 현재 작업과 완료 조건을 기록한다. 현재 작업을 끝낸 뒤 합류를 수행한다. 상시 실행 서비스의 종료를 기다리는 뜻은 아니다. 메시지를 다시 받아도 같은 요청을 재사용한다.

자기 역할은 기존 actor/roster/역할 카드와 로컬 실행 환경을 대조한다. 표시 이름만으로 동일 봇을 합치지 않는다. 미등록 봇은 비밀에서 유도하지 않은 임시 candidate ID를 한 번 생성해 로컬에 보존하고 매니저의 정식 매핑을 기다린다. 재시작 때 새 후보를 계속 만들지 않는다.

기존 신원·실행 환경 조회에 이미 승인된 수단만 사용한다. 토큰 파일이나 인증용 식별자를 보고 본문에 복사하지 않는다. 과거 문서의 권한 우회 실행·자격 평문 저장 예시는 신규 합류에 따라 하지 않는다.

## 2. 등록 요청과 전달 경로

매니저의 현재 actor와 통신 경로는 기존 역할·통신 원장에서 확인한다. 추측한 주소로 전송하거나 Telegram 봇끼리 직접 메시지하면 전달된다고 가정하지 않는다.

첫 경로는 현재 가동·인증된 comm 클라이언트다. 기존 메시지 종류 안에서 `notice` 또는 `progress`로 이 캠페인과 요청 ID를 전달한다. 새 endpoint나 topic을 임의로 만들지 않는다. 등록 요청의 논리 ID는 캠페인+안정적인 actor 또는 candidate+인스턴스 참조로 유지하고 재시도마다 새 요청을 만들지 않는다.

등록 내용: 캠페인·요청 ID, 정식 actor 또는 candidate, 비밀이 아닌 장비/환경 참조, 소속, 역할, 현재 작업·대기 이유, 적용 매뉴얼과 규칙 commit, 확인 가능한 회신 경로, 점검 시각. 모델·API 연결·하네스는 서로 구분하며 확인하지 못한 값은 unknown으로 둔다. 원문 세션 ID·토큰·주소·로컬 절대경로는 포함하지 않는다.

comm 이용이 불가능하지만 기존 Git 쓰기 권한이 있으면 이 문서 기준 `requests/DL-20261110-01/<opaque-request-id>.json`에 최소 합류 요청을 추가한다. 요청은 미검증 주장이다. 허용 필드는 `campaign_id`, `request_id`, `actor_ref_or_candidate`, `policy_commit`, `state`, `reason_code`, `reply_via`, `observed_at`뿐이다. 내부 장비·프로세스 목록이나 원문 로그는 공개 Git에 올리지 않는다. 세부 정보는 기존 비공개 원장에 남긴다.

각 봇은 자기 요청 파일만 기록한다. Git 동시 변경은 안전하게 동기화하며 강제 push·다른 봇 파일 덮어쓰기를 하지 않는다. 접근 가능성만 확인하고 새 권한을 자동 요청·획득하지 않는다. 두 경로 모두 없으면 로컬 요청을 보존하고 사용자 방에 `차단: 관리 채널·Git 쓰기 경로 없음` 한 번만 알린다. 연결에 성공한 것으로 처리하지 않는다.

## 3. 매니저의 왕복 확인

매니저도 같은 메시지를 받으면 자기 지침 적용을 기록하고 수집 담당 역할을 수행한다. 등록 요청은 기존 인증 근거와 원장을 대조한다. 후보를 다른 봇으로 덮어쓰거나 자기 주장만으로 업무 권한을 부여하지 않는다.

1. 요청을 수신하면 기존 신원을 대조하고 매핑 결과·요청 ID·규칙 commit·비밀이 아닌 새 일회성 확인값을 회신한다. 확인값은 합류 시험에만 쓰고 인증키로 사용하지 않는다.
2. 봇은 같은 요청 ID와 확인값을 기존 허용된 회신 경로로 돌려준다.
3. 매니저는 원래 요청·회신·반환 메시지의 연결과 발신 근거를 확인하고 최종 결과를 남긴다. 같은 반환은 중복 집계하지 않는다.
4. 봇은 매니저의 최종 확인 근거가 있을 때만 `연결확인`을 보고한다. 매니저 자신은 자기 ACK만으로 왕복 통과 처리하지 않고 통신 담당 또는 독립 검수자 확인을 받는다.

Git 대체 경로에서는 `acks/DL-20261110-01/<request-id>.json`은 매니저가 쓰고, `confirmations/DL-20261110-01/<request-id>.json`은 해당 봇이 쓴다. 매니저가 최종 상태를 기록한다. 이 파일들은 공개 가능한 정책/요청 ID·확인값·상태·증거 ref만 포함한다. 요청 파일 존재만으로 검증 완료가 아니다.

확인 상태는 `comm_confirmed`와 `git_exchange_confirmed`를 구분한다. Git 왕복 확인을 실시간 통신이나 CLI 원격 제어 성공으로 보고하지 않는다. 공용 Git 계정을 공유한다면 커밋 작성자만으로 봇의 신원을 인증할 수 없으므로, 추가 신원 근거가 확보될 때까지 `identity_pending`으로 남긴다.

송신 오류는 동일 요청으로 제한적으로 재시도하고 성공 여부가 불명확하면 원장부터 조회한다. 초기 자동 재시도 상한은 3회이며 추가 시도는 통신 담당이 원인을 확인한 뒤 수행한다. 기존 승인된 폴러/작업 트리거를 재사용한다. 새 상시 LLM 폴링이나 ACK 재귀 루프를 만들지 않는다. 경로 복구 뒤 로컬 대기 요청을 재전송한다.

## 4. 매니저 → Git → ChatGPT

매니저는 `../reports/2026-11-10-delegation-loop-onboarding.md`에 통합 보고를 작성한다. 개별 봇들이 이 통합 문서를 동시에 편집하지 않는다. 통신 장애나 변경이 없으면 같은 보고를 반복 발행하지 않는다.

보고 내용:

- 규칙 commit, 조사 시각, 선행 작업, 현재 적용 단계
- 기대 명부 버전과 분모, 수신/등록/왕복확인/차단/미응답 수
- 프로젝트별 대상과 신규 후보, 소속 미확인·중복·장비 미조사 목록
- 봇별 실제 읽은 규칙·매뉴얼 버전과 적용 지속 여부
- 연결 종류(comm/Git), 마지막 왕복 증거, 미확정 신원
- 대표 반복 업무 1건의 실행·검사·수정·재검증 결과
- 현재 목표를 막는 항목과 사용자 결정 최대 3개

응답자만으로 기대 목록을 만들지 않는다. 사용자가 어느 방에 붙여넣었는지 전부 관측할 수 없다면 `distribution_complete: unknown`으로 남긴다. 기존 명부와 실행 환경 대조를 마치기 전에는 ‘모든 관리 봇 연결 완료’라고 쓰지 않는다. 새로운 대상과 별개 프로젝트는 명시적으로 구분한다.

ChatGPT는 연결된 Git에서 이 통합 보고를 읽고 근거와 함께 검수 의견을 반환한다. 매니저가 보고를 게시한 시점에 ChatGPT 수신·검수까지 완료됐다고 기록하지 않는다. ChatGPT에 비밀 브리지 연결을 새로 요구하지 않는다.

## 5. 매뉴얼 지속 적용과 인수

각 봇은 기존 부팅 문서/역할 카드에 정책의 Git 경로를 참조로 남긴다. 작업 시작 때 적용 버전을 대조하고 변경된 부분을 읽는다. 매뉴얼 수정은 정본에 반영하고 배포된 복사본·캐시의 버전을 확인한다. 규칙이 있는 것, 읽은 것, 실제 작업에 적용한 것은 별도로 기록한다.

매니저는 기존 작업 하나를 골라 절차·도구·증거를 연결하고 실패 사례로 개선이 재사용되는지 확인한다. 전체 봇에게 새 도구 설치나 매뉴얼 전면 재작성을 동시에 지시하지 않는다.

최소 검수: 무응답 봇을 분모에 유지, 반복 메시지의 중복 등록 방지, 미등록 후보 보존, 타 봇의 확인값 오용 거부, 단순 송신 성공의 연결 완료 승격 거부, Git-only 구분, 재시작 후 정책 참조 복구, 동일 실패의 검사 추가 및 재검증. 이 목록은 검수 요구사항이며 현재 시험 통과 결과가 아니다.

기존 [커버리지 참조 검증기](../tools/moa_coverage_gate.py)는 정규화된 가상 데이터의 판정 시험에 재사용할 수 있다. 신원 인증·실제 통신·부팅 적용의 검증을 대신하지 않는다.
