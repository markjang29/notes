# 관제·게이팅·사이트 통합 — 진단 및 제안 v1 (2026-09-15, 개발팀장 Zcode)

> 이사님 지시: "바로 바꾸지 말고 진단과 제안부터" — 본 문서는 설계안. 승인 후 착수.
> 원칙: 진단은 실측 기반, 제안은 기존 정본(topology-graph-v1, homeserver-target-design-v1,
> conversation-rules-v1 제11~13조, RELAY-63)과 무모순하게 연결.

## 1. 진단 — 무엇이 문제인가

### 1-1. 게이팅이 작동하지 않았다 (구조적 증거)
- **RELAY-15/17/18/43~48 (8건)**: "포트 단속·소급등록" — **티켓 없이 운행된 서비스가 8개 이상**.
  승인보드(8005)와 JIRA가 있었지만 발행 전 개발이 가능했고, 단속은 사후에만 이루어짐.
- **RELAY-37 (빈화면 사고)**: 게이트에 테스트 커버리지 명세가 없어 사고가 배포를 뚫음.
- 원인: ① 발행 창구가 사람(매니저 경유) 수작업 ② 상태가 "해야 할 일" 하나로 평탄해서
  **의사결정 대기와 구현 대기가 구분 안 됨** ③ 배포·승인과 티켓이 시스템으로 연결 안 됨.

### 1-2. 미의사결정이 쌓여 있다 (RELAY 51건 중 분류)
| 유형 | 티켓 | 특징 |
|---|---|---|
| **ADR/설계 판정 대기** | RELAY-10(월드 스모크 ADR)·11(감독 개입 계약)·23(렌즈 개념)·25(PORTAL 설계)·37(게이트 명세 안건)·49(파이프라인 정본)·53(커버리지 엔진) | 이사님 판정 없이는 구현 불가 — 구현 큐와 섞여서 표류 |
| 소급 등록(이미 개발됨) | RELAY-17·18·43~48 | 사후 승인형 — 담당 정합성 미확인 |
| 검증 대기 | RELAY-1(TRACK-1 이사님 체험 승인)·29(P-4 실사 게이트)·7(NEXT 품질시험) | 게이트 통과 증거 없음 |
| 순수 구현 잔여 | RELAY-2·5·21·24·31·34~36·38~42·51·52·54~56 등 | 담당 배정·우선순위 필요 |

### 1-3. 기술 스택 실태 (사이트 27개 등록 기준)
- **Spring Boot+React: 2개뿐** (8024 포털, firebat 8766). **Python HTML/JS: ~20개**
  (Flask/FastAPI/stdlib HTTP 혼재, 템플릿도 제각각).
- 일부 서비스가 **repo가 아니라 과거 release 사본에서 운행**: 8006(~/releases/scenario 옛 커밋),
  8008(~/matrix-candidate/releases), 8009(~/apps/rpg-game-01-home) — 코드 정본과 런타임 괴리.
- 8011·8017: 레거시 판정 대기 방치.
- RELAY-63(react-best-practices 전사 적용)·64(게임 사이트 설계 통합)가 이미 방향 합의됨 — 미집행.

### 1-4. 소통·테스트 구조
- 회의방(8023/8026) 소통은 활성. 그러나 **발언→티켓 자동화 없음**(conversation-rules "이사님 발언=요구사항"이 수작업).
- 테스터 봇(`@heav_gmwin_codex_bot` 97_[GM윈도][테스터])이 명단에 있으나 **게이트 역할 부여 안 됨**.
- Taiga 현재: 단일 RELAY 프로젝트·평면 칸반 — 위 계층(의사결정/담당/게이트)을 표현 못 함.

## 2. 제안 — Taiga 구조 재편 (이름: Taiga, "타이가"가 맞습니다)

### 2-1. 프로젝트 4분화 + 에픽
| 프로젝트 | 내용 | 에픽 예 |
|---|---|---|
| **GOV** (관제) | 포트 단속·승인·게이트 운영·규칙 | 단속, 승인보드 연동, 게이트 명세 |
| **PIPE** (자산 파이프라인) | TRACK-1/2, P-1~7, ARCA2RISU | 기존 TRACK/P 체계 그대로 에픽화 |
| **SITE** (사이트 통합) | Spring 통합·React 전사·모바일 | RELAY-63/64, 마이그레이션 웨이브 |
| **INFRA** (인프라) | 백업·허브·엣지·방화벽 | 이관 잔여, 백업 허브, client_id |

기존 56티켓은 유형별로 4프로젝트로 이동(키 [RELAY-nn]은 유지되므로 소급 대조 가능).

### 2-2. 상태 = 게이팅 파이프라인 (핵심)
```
접수 → 요구정의 → 의사결정대기(ADR) → 설계 → 구현 → 테스트봇검증 → 이사님승인 → 배포 → 폐기
```
- **의사결정대기**와 구현을 분리 — 이사님 큐는 "의사결정대기" 상태만 보면 됨.
- 커스텀 필드: `원천발언일`·`담당봇`(roster 정본 매핑)·`사이트/포트`·`repo`·`게이트증거`(테스트 리포트 링크).
- 위키: 각 프로젝트에 ADR 인덱스 + 아키텍처 원칙 (notes repo 정본 링크, 중복 금지).

### 2-3. 게이팅 자동화 (봇 3역할)
1. **소통봇(회의방 hub)**: `@티켓` 커맨드로 발언→Taiga Story 자동 생성(접수 상태).
   이사님 "이사님 발언=요구사항" 규칙의 기계화.
2. **테스팅봇(@heav_gmwin_codex_bot)**: "테스트봇검증" 상태 polling → 사이트 헬스체크·핵심 플로우
   실측 → 리포트를 Taiga 댓글+상태 전이 (통과/반려). RELAY-37 재발 방지.
3. **감사봇(@heav_lnx_audit_bot)**: 미등록 포트·티켓 없는 배포 단속 (RELAY-15 상시화) —
   엣지 nginx 라우트와 Taiga 프로젝트 대조, 위반 시 GOV 프로젝트에 자동 티켓.
4. **승인보드(8005) ↔ Taiga**: 판정 O/X 시 webhook으로 상태 자동 전이 (이사님승인 단계).

### 2-4. Spring Boot 통합 + 온톨로지향 (SITE 프로젝트 로드맵)
- **단일 진입**: 8024 Spring Portal = 게이트웨이+BFF. 파이썬 페이지 3분류 처리:
  - (a) 정적·조회형(홈·현황판·갤러리류) → Spring+React로 흡수 (1차 웨이브)
  - (b) 계산·데이터 처리형(워크벤치·엔진) → Spring이 프록시하는 사이드카로 존치, 차후 포팅 판정
  - (c) 폐기 후보(레거시 8011·8017·중복 화면) → 의사결정대기 티켓으로 승격
- **온톨로지 원장**: 자산·사이트·봇·티켓·repo·포트를 노드로 연결(topology API 23nodes 확장).
  Taiga 커스텀 필드와 topology 그래프가 같은 어휘(repo/포트/담당봇)를 공유 —
  "이 사이트는 어느 티켓에서 왔고 누가 담당하고 어느 repo가 정본인가"가 기계 조회됨.
- **React 전사**: RELAY-63 스킬 기준으로 신규는 React SPA + Spring API만 허용(게이트가 강제).
  파이썬 신규 페이지 금지 조항화.

### 2-5. 단계 로드맵 (승인 후)
| Phase | 내용 | 공수 |
|---|---|---|
| 0 | 본 제안 승인·우선순위 확정 | 이사님 |
| 1 | Taiga 4프로젝트 재편 + 56티켓 이동 + 상태/필드/위키 | 1일 |
| 2 | 게이팅 자동화: 소통봇→Taiga 생성, 테스팅봇 polling, 승인보드 webhook | 2일 |
| 3 | Spring 통합 1차 웨이브(정적형 흡수 후보 선정·설계 문서) | 2일+ |
| 4 | 파이썬 잔존 포팅/폐기 판정(의사결정 티켓 일괄) | 이사님 판정 병행 |
| 5 | 온톨로지 원장 완성(topology↔Taiga 동기화) | 2일 |

### 2-6. 리스크·롤백
- Taiga 재편은 기존 [RELAY-nn] 키 보존 설계라 언제든 재분류 가능.
- 게이팅 자동화 전 단계는 수작업 병행(봇 장애 시 게이트가 막히지 않게 fallback).
- Spring 통합은 웨이브별 컷오버, 웨이브 직전 상태로 롤백 가능(release 디렉터리 불변).
