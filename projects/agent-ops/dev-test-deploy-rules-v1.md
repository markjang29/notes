# 개발-검증-배포 규칙 v1 (전 봇 공통)

> 이사님 09-20 지시 — CI/CD 관점 일반화. 모든 봇이 봇별 서비스에 동일하게 적용한다.

## 1. 환경 3층 분리

| 층 | 위치 | 용도 | 접근 |
|---|---|---|---|
| dev | 자기 기계 · 임시 포트 | 개발·빌드 — 항상 최신, 깨져도 무방 | 해당 봇만 |
| staging | 자기 기계 · 고정 포트 | 테스터 검증 + 이사님 미리보기 — 기능 완성본만 | 테스터 + 이사님 |
| prod | 공식 진입점(8024 하위 등) | 운영 — 승인된 것만 | 전원 |

- 각 봇은 자기 서비스의 3층 포트를 지정해 관제방에 보고한다.
- dev에서 staging으로 올리는 시점은 "자체 테스트 전 구간 통과 후"만 허용한다.

## 2. 개발 흐름 (순서 절대)

1. dev에서 개발
2. 자체 테스트: 화면 표시 → API 응답 → **실제 데이터가 화면에 보이는지 눈으로 확인**
3. staging에 반영 (테스터가 접근 가능한 상태로)
4. 테스터(지정 봇)에게 허브 task로 검증 요청
5. 테스터 통과 보고 → 이사님께 결과 보고 (staging 링크 첨부)
6. 이사님 "배포" 지시 → prod 반영

## 3. 보고 규칙

- "완료"는 **staging에서 테스터 통과 후**에만 사용한다. 그 전에는 "staging 반영"이라고만 한다.
- "반영 완료"는 **prod에서 실제 동작 확인 후**에만 사용한다.
- 링크 보고 시: staging 링크 + prod 링크를 구분해서 전달한다.

## 4. 자체 테스트 체크리스트 (최소)

- [ ] 페이지 로드 (제목·화면 구성 확인)
- [ ] 핵심 기능 동작 (버튼 클릭 → 의도한 결과 표시)
- [ ] 신규 데이터가 실제로 화면에 보이는지 (API 숫자만 확인하지 말 것)
- [ ] 기존 기능 회귀 (예전 기능이 안 깨졌는지)

## 5. prod 배포 규칙

- 공유 서비스(8024 등) 배포 전 해당 서비스 오너(봇)에게 허브로 협조 요청
- 배포 후 공인 경로 실측 → 결과 회의방 보고
- 롤백 가능 상태 유지 (git tag 또는 릴리즈 디렉터리 스냅샷)

## 6. 위반 시

- staging 미거쳐 prod 직행: 즉시 롤백 + 경고
- "완료" 오남용: 보고 무효 — 재검증 후 재보고
