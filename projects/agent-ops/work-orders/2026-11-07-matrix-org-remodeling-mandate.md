# 목표와 위임

## 1. 사용자 의도 — 이번 작업의 판단 기준

사용자는 ChatGPT의 제한된 토큰을 설계 판단과 결과 검수에 집중시키고,
매니저와 각 봇이 상세 조사·구현·검증을 맡기를 원한다.
최우선 제품 목표는 사용자가 선택한 **매트릭스 엔진 중심**이다.

제품 흐름은 원천 데이터 → 검증·가공된 코어 자산 → 매트릭스 엔진의 인물·월드 생성과 상호작용
→ RPG 등 소비 서비스 → 엔진으로의 상호작용 피드백이다.
가공 코어 자산과 엔진이 생성한 창작물을 구분하며, 화면상의 연결만으로 구현 완료를 주장하지 않는다.

후속 목표는 구조 전반을 **Docker·Kubernetes 기반으로 리모델링**하는 것이다.
사용자가 코드를 최소한으로 살펴보면서도 각 봇이 만든 사이트의 통신·데이터 흐름을 추적하고,
할 일·담당자·검수·승인·배포가 지속적으로 관리되어야 한다.
Jira 무료 사용 종료로 관리 도구 교체가 필요하며, 같은 이유로 다시 이전하는 구조를 피한다.

실패 경험을 되풀이하지 않는다:
- 여러 포트·사이트·저장소의 관계와 책임자가 불명확함.
- 원천·실제 처리 없이 보이는 화면만 완성됨.
- 작업·승인 기록이 흩어지고, 큰그림을 매번 수작업으로 다시 작성함.
- 많은 사칙·문서·도구를 추가해도 일상 운영과 실제 구현이 연결되지 않음.

## 2. 책임과 결정권

| 주체 | 책임 | 사용자에게 넘기지 않을 일 |
|---|---|---|
| 사용자 | 제품 목적·우선순위·비용·되돌리기 어려운 변경 결정 | 모든 코드와 보고서의 세부 검토 |
| ChatGPT | 사용자 의도 유지, 대안·트레이드오프 설명, 통합 보고의 모순·증거 표본 검수 | 저장소 전체 재탐색·상시 폴링 |
| 매니저 | 조사 분담, 작업 단일 목록, 의존성·충돌 조정, 복구, 통합 보고와 완료 책임 | 봇별 질문을 그대로 사용자에게 전달 |
| 담당 봇 | 자기 범위 조사·구현·테스트와 증거 제출 | 다른 봇에게 책임 전가·재귀적 무한 위임 |
| 검수 담당 | 구현과 구분되는 검수 관점, 실제 근거 확인 | 구현자의 완료 선언을 그대로 승인 |

ChatGPT가 오프라인이어도 합의된 범위의 작업은 매니저가 이어간다.
모든 사소한 수정의 승인을 사용자나 ChatGPT에 집중시키지 않는다.
조직 자체의 기술·업무 제약과 반론은 근거와 함께 기록하며 무조건적인 동의를 완료 조건으로 삼지 않는다.

## 3. 이번에 실행할 범위

1. 전체 조사 및 의도 불일치 분류.
2. 중복·잘못된 링크·명백한 상태 오류 등 근거 있는 가역적 문서 정리.
3. 격리 브랜치/테스트 환경에서의 작은 수정과 검증, draft PR 또는 이에 준하는 검토 묶음.
4. 목표 구조, 운영 방식, 단계별 이행 계획과 첫 실증 작업 제안.
5. 봇별 이해 확인과 매니저의 통합 보고.

운영 데이터 삭제, Git 이력 재작성, 계정/봇 폐기, 서비스 종료, 대규모 일괄 배포·DB 이전,
비용 발생, 보안 경계 확대는 구체적인 영향·롤백·검증 근거를 먼저 준비하여 사용자 결정으로 올린다.
발견만으로 전체 개발을 중단시키거나 임의로 프로젝트를 폐기하지 않는다.
이번 조사를 근거로 안전한 작업은 계속 진행하고 결정이 필요한 항목만 따로 보류한다.

## 4. 매니저의 첫 조치

- 이 작업을 실제 수신한 신원으로 ACK하고, 위임 범위와 완료 조건을 자기 말로 설명한다.
- 기존 통신 점검 command_id `3b9d4da5-e79e-40d9-a8ae-d11be6169e1d`를 본 조사에 연결한다.
  기존 probe를 다시 보내지 않는다. 먼저 그 작업의 ACK/진행/결과 누락을 해소한다.
- ChatGPT 실제 왕복 확인 command_id `ba939cc7-5543-43e0-8a53-6c5c086cd8dd`의 submitted 이벤트를 재사용한다.
  이 이벤트는 존재하지만 GET command의 result가 null인 관측도 조사한다. 전송 성공·회신·검수는 별도다.
- ACK 후 10분 내 분담표와 첫 확인 근거 또는 정확한 막힘을 남긴다. 시간만 지나면 완료로 처리하지 않는다.
- 담당 봇과 검수 봇을 실등록 신원·가용성·권한에 맞춰 선정한다. 초기 동시 실행은 3개 이내로 두고
  실측 자원·쿼터에 따라 조절한다. 토큰이 상대적으로 많다는 말을 무제한 사용으로 해석하지 않는다.
- 로컬 사칙의 검증 루프는 매니저가 각 봇을 통해 수행하고, 주요 보고·변경안은 서로 다른 관점의
  2회 검토와 반영 근거를 남긴다. ChatGPT에 같은 원문 전체를 반복 전달하지 않는다.

## 5. 조사와 정렬

봇/서버/저장소 원장과 실제 배포를 대조하여 조사 대상을 확정한다.
정의된 대상 수, 확인 수, 미확인 수와 이유를 함께 기록해 “전체 조사”의 범위를 검증 가능하게 한다.
오래된 문서의 상태를 현재 사실로 간주하지 않는다.

### 봇과 실행 환경

- 역할, 실제 transport 신원, 서버, 프로세스·sidecar·poll·wake·ACK·결과 경로.
- 실제 client/backend/model/token pool과 확인 가능한 사용량·오류. 비밀값과 추정 잔여량 제외.
- 통신 점검은 기존 지시의 봇당 최대 1건, 동시 probe 최대 2건을 유지한다.
- 미가동·동결·wake=false·등록 충돌은 구분하고 임의 재활성화하지 않는다.

### Git과 제품

- 등록/발견된 관련 저장소, 소유자, 기본 브랜치, 열린 브랜치·PR, 미커밋·미푸시 변경,
  코드 full commit, 배포 full commit, CI/테스트, 실제 사용자 경로, 현재 작업.
- 미커밋 변경은 소유자를 확인하고 보존한다. 세션·문서·배포 버전 불일치를 명시한다.
- 원천 입력부터 코어 자산·엔진·RPG까지 실제 데이터와 호출이 이어지는지 확인한다.
- 예시 데이터, fixture, 정적 화면, 미연결 API와 실자료 기반 구현을 명확히 구분한다.
- 기존 Prefect 명세/구현, Spring·React 이관, 통신 브리지는 선행 투자로 검토한다.
  사용자 목표 기여와 동작 근거 없이 전부 재작성하거나 무조건 유지하지 않는다.

### 할 일·승인

- Git/기존 관제/Jira/문서/봇 세션에 흩어진 관련 작업·승인 대기를 조사한다.
- 접근 불가 Jira 데이터는 미수집으로 기록한다. 내보내기와 이전 경로를 확인하고 복구를 꾸미지 않는다.
- 중복 작업은 원 ID를 보존해 연결하고, 상태 변경 이유·근거·책임자를 남긴다.
- 하나의 작업에 하나의 현재 상태·책임자·완료 조건을 둔다.

불일치 목록은 영향이 큰 순으로:
`사용자 의도 / 관측된 실제 / 근거 / 사용자·제품 영향 / 원인 / 처리안 / 담당 / 검증 / 결정 필요 여부`.
처리안은 유지·수정·통합·보류·폐기 제안으로 분류하며 제안을 실행 결과로 표시하지 않는다.

## 6. 목표 구조와 리팩토링 계획

다음 세 가지를 연결하되 각각의 역할을 분명히 한다.

1. **서비스 실행:** Docker 이미지와 Kubernetes 워크로드, 배포 버전·자원·네트워크·저장소·백업·복원.
2. **추적:** 서비스/데이터의 정적 의존 관계와 실제 요청·작업의 실행 이력.
3. **업무 운영:** 목표·작업·검수·승인·코드·배포·실행 증거를 연결하는 관리 원장.

Kubernetes만으로 업무·승인 관리까지 해결됐다고 판단하지 않는다.
현재 N100 3대의 실제 가용 메모리·디스크·권한·네트워크·상시 운영 가능 여부를 확인하고,
적정 Kubernetes 구성과 제약을 비교하라. 기술 선택은 현재 공식 문서·라이선스와 실측 근거를 함께 제시한다.
운영 클러스터 설치·이전은 조사 완료만으로 자동 착수하지 않는다.

사용자가 한 사이트를 선택했을 때 다음을 확인할 수 있는 경로를 설계한다:
`기능 목적 → 책임 봇 → 소스 저장소/커밋 → 배포 이미지/버전 → 입력·출력 계약
→ 호출 상대 → 실제 요청/작업 추적 → 관련 작업/승인/검증`.
최소 표준은 식별자, API·메시지 계약, 상관 ID, 상태/오류, 실행 시각, 코드·배포 버전이다.
비밀과 민감한 본문을 추적 데이터에 수집하지 않는다.

구성도는 등록 정보·배포 명세·API/메시지 계약·실행 관측에서 생성/검증하고,
사람이 지정한 관계와 실제 관측한 관계를 구분한다. 수작업 그림 하나를 별도 정본으로 유지하지 않는다.
서비스 관계, 데이터 계보, 작업 실행 관계를 한 그림에 모두 섞지 않고 필요에 따라 보게 한다.

Jira 대안은 기존에 쓸 수 있는 원장을 우선 검토하고 필요하면 후보 최대 3개만 비교한다.
자체 호스팅/지속 무료 조건, 실제 라이선스, 작업·승인 모델, API·봇 연동, Git 연결,
백업·복구·내보내기, N100 자원과 운영 비용을 평가한다.
사용자에게 여러 도구의 원장을 동시에 관리하도록 요구하지 않는다. 도구 선정 전 새 관리 시스템을 양산하지 않는다.

이행은 단계별로:
- 현황과 기준선 확정.
- 작은 대표 기능 1개를 골라 작업·승인·코드·컨테이너·배포·추적을 끝까지 연결.
- 그 결과에 따라 서비스별 이전 물결과 의존성 확정.
- 실제 동작·데이터 보존·롤백을 검증한 뒤 기존 경로 종료 제안.

각 단계는 선행 조건, 담당, 관찰 가능한 완료 조건, 검수자, 복구 방법과 중단 기준을 가진다.
전면 재작성·일괄 전환 계획으로 대체하지 않는다.

## 7. 조직이 이해하는 운영 방식

각 봇은 짧은 역할 확인서를 자기 말로 회신한다:
- 우리 제품의 목적과 내가 기여하는 결과.
- 내가 받는 입력, 만드는 출력, 의존하는 상대.
- 내 권한과 완료를 입증할 방법.
- 현재 목표와 어긋난 점, 제약 또는 이견.
- 다음 한 가지 실행과 책임자.

매니저는 답변의 모순과 역할 중복·공백을 조정한다. 단순 “이해했습니다”는 충분하지 않다.
사용자에게는 코드 설명 대신 실제 사례 하나로
“요청 → 분담 → 구현 → 검수 → 필요한 승인 → 배포 → 동작 확인 → 종료”를 설명한다.
사소한 가역적 작업은 위임된 기준으로 진행하고, 의미 있는 제품 선택·비용·비가역 변경만 질문한다.
반복되는 질문은 결정 기록과 후속 지시로 연결해 새 세션에서도 다시 묻지 않도록 한다.

## 8. 보고와 지속성

매니저가 상세 원장을 보유하고 ChatGPT에는 **변경분 중심 요약**을 보낸다.
기본 보고는 1,500자 이내로 하고 원문 로그는 필요한 근거 링크만 포함한다.

필수 필드:
- 현재 단계·가장 중요한 발견·실제 끝난 일.
- 전체 조사 대상/확인/미확인 수.
- 의도 불일치 상위 5개와 우선 정리 대상.
- 담당/상태/막힘/다음 행동.
- 사용자 결정 최대 3개: 선택지, 매니저 추천, 영향, 기한이 필요한 실제 이유.
- 보고서 Git 링크와 full commit, 관련 command/task/PR ID.

첫 보고는 수신·분담·첫 증거이고, 이후 조사 통합 보고와 변경 검증 보고를 같은 부모 작업에 연결한다.
운영 점검 재요청이나 ChatGPT의 반복 폴링에 의존하지 말고 서버 측에 작업 상태·진행 증거를 보존한다.
한 번의 조사와 정리 이후에도 상태가 실제 실행에서 갱신되는 절차·담당·실패 알림을 정의한다.
새 상시 스케줄/외부 알림이 필요하면 빈도·자원·중복 방지를 계획에 명시하고 임의로 대량 생성하지 않는다.

기존 관리 정본을 재사용하고, 신규 공통 문서는 이 지시·통합 현황·이행 계획 정도로 제한한다.
보고서는 notes의 projects/agent-ops/reports/ 아래에 저장하고 상세 제품 변경은 해당 제품 Git에 둔다.
이 작업의 bridge 회신에는 command_id와 result 객체 안에 summary, report_url, full_commit_sha,
stage, coverage, findings, decisions_needed, next_actions를 넣는다.
장기 작업의 중간 결과는 progress로 보내며, “계획 작성”만으로 전체 리모델링을 submitted/완료 처리하지 않는다.
현재 단계의 조사·가역적 정리가 끝나면 그 범위만 명시하여 제출한다.

## 9. 완료 판정

이번 단계:
- 조사 범위와 누락이 명확하고, Git·배포·통신 증거로 현재 상태를 설명할 수 있다.
- 매트릭스 목표와 불일치하는 항목이 우선순위·책임자·처리안과 연결돼 있다.
- 안전한 정리의 전후·검증이 남아 있고, 위험한 변경은 구체적인 결정안으로 준비돼 있다.
- 매니저와 담당 봇의 역할 이해·이견·조정 결과가 있다.
- 첫 대표 기능과 단계별 리모델링 계획을 사용자가 이해할 수 있다.

목표 운영 구조의 실증:
- 임의의 대표 사이트 요청 하나에서 실제 호출 상대·실행/오류·소스/배포 버전을 추적할 수 있다.
- 그 변경의 요청·담당·검수·승인·배포 상태를 한 작업 ID에서 찾을 수 있다.
- 봇/매니저/ChatGPT 세션이 끊겨도 중복 실행 없이 상태와 다음 행동을 복구할 수 있다.
- 사용자는 코드 전체나 여러 현황판을 읽지 않고 중요한 결정과 막힌 일을 파악할 수 있다.
