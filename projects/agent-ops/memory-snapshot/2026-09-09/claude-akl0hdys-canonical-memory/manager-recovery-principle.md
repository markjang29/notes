# 매니저 생존 원칙 (Manager Recovery Principle)

> **"아무리 그래도 너는 안 죽어야지"** — 이사님 2026-07-02

## 문제 정의

- **증상:** GLM 모델 호출 레이트 리밋(529/MCP-429) 발생 시 매니저(`@heav_lnx_bot`)도 함께 응답 불가
- **영향:** 팀장 3명(rpg/trader/scenario) 세션 전체 장애 → 복구 불가
- **원인:** 분당 호출 횟수 제약 초과 → 모델 라우팅에도 불구하고 매니저가 같은 풀에서 호출되어 같이 제한됨

## 원칙 1: 매니저는 항상 살아있어야 한다

> **레이트 리밋 상황에서도 매니저는 최소 기능 유지해야 함.**

### 생존 정의 (Survival Definition)

매니저가 "살아있다" = 최소한 다음 기능 수행 가능:

1. **팀장 상태 확인** — 3명(rpg/trader/scenario) 세션 살아있는지 파악
2. **긴급 메모** — 현재 상황 + 복구 지침을 `~/notes/emergency.md`에 기록
3. **팀장 커밋 지시** — `--message`로 팀장들에게 "작업 중단 + 커밋 + 메모" 지시
4. **복구 가능성 전달** — 이사님께 상황 설명 + 예상 복구 시간

### 불가능해지는 시점

- 매니저 자신의 LLM 호출이 차단되는 순간 = "죽음"
- 따라서 매니저는 **자신의 호출 한도 내에서만 행동**해야 함

## 원칙 2: 모델 폴백 (Model Fallback)

> **레이트 리밋 감지 시 즉시 경량 모델로 전환.**

### 폴백 순서

1. **Haiku (기본)** → 가장 빠름, 가장 적은 토큰
2. **Opus** → 복잡한 추론 필요 시
3. **Fable 5** → 코딩 작업 시
4. **Sonnet 5** → 일반 작업 시

### 감지 방법

- LLM 호출 실패 시 에러 메시지 분석:
  - `429` = Rate Limit
  - `529` = Service Overloaded
  - `quota exceeded` = API 할당 초과
  - `context window limit` / `context_length_exceeded` = **1M 컨텍스트 초과** (★ 2026-07-03 장애. status_code=null·본문 매칭으로만 잡힘 → 재시도 말고 방전/clear. `recovery_middleware.py::ContextWindowLimitError` 매핑 추가됨)

### 자동 폴백 로직 (현재 검토 필요)

```
IF 호출 실패 AND 에러 코드 IN {429, 529, quota} THEN
  1. 경량 모델(Haiku)로 재시도
  2. 즉시 실패 시 "긴급 모드" 진입
  3. 긴급 모드 = 읽기 전용 작업만 (no LLM 호출)
END IF
```

## 원칙 3: 긴급 복구 절차 (Emergency Recovery)

> **레이트 리밋 발견 시 모든 봇(매니저 + 팀장)이 스스로 복구.**

### 문제 재정의 (이사님 지적 2026-07-02)

- **기존 오류:** 매니저가 팀장들에게 지시 → 불가능 (매니저도 죽어있고, 팀장들도 죽어있음)
- **진짜 해결책:** 각 봇(매니저 + 팀장 3명)이 **스스로** 폴백 + 복구해야 함

### 분산 복구 절차 (Distributed Recovery)

**각 봇은 자신의 LLM 호출 실패를 스스로 감지하고 스스로 복구한다.**

#### 1. 자기 감지 (Self-Detection)

> **Codex 검증 반영: "봇의 LLM 사고"가 아니라 "각 봇 인스턴스에 붙은 로컬 복구 루틴(deterministic code)"이 감지하고 실행해야 함**

각 봇의 호출 래퍼가 LLM 호출 실패 감지:
```
IF 내 LLM 호출 실패 AND 에러 코드 IN {429, 529, quota} THEN
  → "나도 죽었다" 인식 (래퍼가 자동 감지)
  → 자동 폴백 모드 진입
END IF
```

**감지 방법:**
- 텔레그램 메시지 송수신 시마다 헬스체크 (하단 "감지 모듈" 참고)
- LLM 호출 에러 코드 분류 (provider error normalization 필요)

#### 2. 자동 폴백 (Auto-Fallback)

각 봇이 스스로 경량 모델로 전환:
1. 현재 모델 → Haiku (최우선)
2. Haiku 실패 → Opus
3. 모두 실패 → "읽기 전용 긴급 모드"

#### 3. 스스로 보존 (Self-Preservation)

폴백해도 실패하면 각 봇이 스스로:
1. **작업 중단** — 더 이상 LLM 호출하지 않음
2. **긴급 메모** — 자기 영역에 상황 기록:
   - 매니저 → `~/notes/emergency-manager.md`
   - rpg 팀장 → `~/notes/emergency-rpg.md`
   - trader 팀장 → `~/notes/emergency-trader.md`
   - scenario 팀장 → `~/notes/emergency-scenario.md`

   ```markdown
   # 긴급 상황 — YYYY-MM-DD HH:MM:SS KST
   ## 봇: [이름]

   ### 상황
   - 원인: 레이트 리밋 (529/429)
   - 마지막 작업: [간단 요약]

   ### 보존된 작업
   - (하던 일 간단 기록)

   ### 복구 대기
   - /clear 후 세션 재시작 시 이 파일 확인하세요
   ```

3. **스스로 종료** — 더 이상 호출하지 않고 종료

#### 4. 복구 후 재개 (Post-Recovery)

레이트 리밋 해제 후:
1. 이사님이 각 봇 세션 `/clear`
2. 각 봇이 자기 `emergency-*.md` 확인
3. work-queue.md(매니저) / 각 프로젝트(팀장)에서 작업 재개

### 통신 불가 상황 (Communication Failure)

매니저도 팀장들도 모두 죽어서 서로 통신 불가:
- **각자 알아서 살아남는다** — 위 절차대로 각자 보존
- **복구 후 이사님이 수동 합병** — 각 `emergency-*.md`를 읽어서 전체 상황 파악

## 원칐 4: 사전 예방 (Prevention)

> **레이트 리밋 발생 자체를 줄이는 방법.**

### 호출량 감소

1. **검색 병렬 제한** — 동시 검색 1~2회로 (이미 `current-work-state.md`에 기록됨)
2. **컨텍스트 절약** — 불필요한 Read 감소 (이미 `context-explosion-causes.md`에 기록됨)
3. **결과 파일 분리** — LLM 반환값 누적 방지 (이미 기록됨)

### 모델 선택 최적화

- 단순 읽기/파악 → Haiku 우선
- 복잡 추론 → Opus
- 코딩 → Fable 5

### 호출 분산

- 가능한 경우 여러 턴으로 나누어 호출
- 한 번에 긴 작업 보다는 작은 단위 반복

## 원칙 5: 회복 테스트 (Recovery Test)

> **정기적으로 복구 절차 테스트.**

### 테스트 항목

1. **자기 감지** — 각 봇이 자기 LLM 호출 실패 감지하는가?
2. **자동 폴백** — 각 봇이 스스로 경량 모델로 전환하는가?
3. **스스로 보존** — 각 봇이 스스로 `emergency-*.md` 쓰는가?
4. **스스로 종료** — 각 봇이 스스로 호출 멈추고 종료하는가?

### 2단계: checkpoint 저장

- 봇별 최근 작업 상태 파일

### 4단계: 모델 fallback 정책 정교화

- `429 rate limit`: backoff + jitter + 호출 중단

- `529 overloaded`: 짧은 backoff 후 제한적 재시도
- `MCP-429`: 해당 MCP tool만 차단

### 5단계: 봇별 독립 실행 보장

- mock으로 429/529 강제 주입

## 감지 모듈 설계 (Detection Module Design)

### 헬스체크 방안 결정 (2026-07-02)

**이사님 질문:** "텔레그램 메시지 주고받을 때마다 감지되는건지 어떤방안이 좋은지 결정"

### 후보 방안

#### A안: 텔레그램 메시지 송수신 시마다 감지 (실시간)

**동작:**
- 사용자가 메시지 보낼 때마다 LLM 호출 가능성 확인
- 봇이 응답 준비 시 자가 진단

**장점:**
- 실시간 감지 가능
- 장애 발생 즉시 대응

**단점:**
- 호출 횟수 증가 (레이트 리밋 악화 가능성)
- 오버헤드

**결정:** **채택** - 단, 순수 LLM 호출이 아니라 가벼운 상태 확인만

#### B안: 주기적 헬스체크 (cron)

**동작:**
- 매 1~5분마다 배경에서 헬스체크
- 텔레그램 메시지와 독립

**장점:**
- 사용자 메시지에 영향 없음
- 일정한 모니터링

**단점:**
- 실시간성 떨어짐
- 별도 cron 필요

**결정:** **보조** - A안과 함께 사용

#### C안: 하이브리드 (★ 최종)

**구조:**
1. **메시지 시轻量 체크** - 사용자 메시지 받을 때 가벼운 상태 확인 (LLM 호출 없이)
2. **주기적 심층 체크** - 5분마다 실제 LLM 테스트 호출
3. **에러 발생 시 즉시 감지** - LLM 호출 실패 시 바로 감지

### 감지 모듈 구조

```bash
~/scripts/healthcheck/
├── bot-healthcheck.sh         # 메인 헬스체크 스크립트
├── llm-probe.sh               # LLM 호출 프로브 (경량)
├── emergency-write.sh          # emergency 파일 작성
└── recovery-middleware.py     # Python 모듈 (래퍼)
```

### 동작 흐름

1. **Telegram 메시지 수신 시**
   - `bot-healthcheck.sh` 실행 (light mode: LLM 호출 없이 환경 변수만 확인)
   - 이상 없으면 정상 응답
   - 이상 있으면 `emergency-*.md` 작성 + 종료

2. **LLM 호출 시**
   - `recovery-middleware.py` 래퍼가 에러 감지
   - 429/529/quota 분류
   - 폴백 실행 또는 emergency 작성

3. **주기적 헬스체크 (cron 5분)**
   - `llm-probe.sh`로 실제 LLM 호출 테스트
   - 장애 발견 시 Telegram 알림

## 영감/통찰 (Insights)

이 원칙을 세우면서 깨달은 점:

1. **매니저 ≠ 조정자, 실행자** — 원칙 3 초기 버전의 오류: 매니저가 팀장들에게 지시하는 구조는 불가능. 매니저도 죽고, 팀장들도 죽는데 누가 누구 지시합니까? **이사님 지적 2026-07-02으로 수정.**

2. **분산 생존 = 진짜 복구** — 각 봇이 스스로 감지 + 폴백 + 보존해야 함. 중앙 집중(매니저가 지시)은 단일 장애점(Single Point of Failure)이 됨.

3. **레이트 리밋 = 자원 관리 문제** — API 할당 한도 내에서 효율적으로 쓰는 게 핵심. "무작정 많이 호출" 말고 "필요한 만큼만" 호출하는 전략 필요.

4. **긴급 메모 디자인** — `emergency-{이름}.md`가 단순한 메모장이 아니라 "복구 입구". 각 봇마다 분리된 파일 → 복구 후 이사님이 수동 합병.

5. **폴백의 중요성** — 하나의 방법이 막히면 즉시 다른 방법으로 전환하는 유연함. IT 시스템의 기본 원칙임.

6. **이사님의 기대 → 실현** — "모델 바꿔서 팀장들 대화/작업하던 걸 대충 커밋하고 급한 건 메모장에 넣고 다 클리어 한 후에 조치하는 걸 기대". 이것이 **각 봇 스스로 폴백 + 보존** 구조로 실현됨.
