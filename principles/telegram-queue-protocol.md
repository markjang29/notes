# 사칙 — Telegram 큐 수신·응답 규칙

## 1. 한 줄 원칙

이사님이 Telegram에서 `큐시작`을 보내면 봇은 긴 입력 수신 모드로 들어가고, `큐끝`을 받을 때까지
분석·실행·답변을 하지 않는다.

ELI5: 택배 상자가 여러 개 올 때는 마지막 상자(`큐끝`)가 도착하기 전까지 뜯어 정리하지 않는다.

## 2. 트리거

- `큐시작`: 현재 대화에서 큐 수신 모드 시작.
- `큐끝`: 지금까지 받은 큐 조각을 순서대로 하나의 입력으로 보고 처리 시작.
- 트리거는 앞뒤 공백을 제거한 뒤 정확히 일치할 때만 적용한다.
- 큐 수신 중간 메시지는 작업 지시로 실행하지 않는다.

## 3. 수신 중 행동

- `큐끝` 전에는 중간 요약, 반박, 실행, 파일 작성, Git 변경, 스케줄 등록, 외부 전송을 하지 않는다.
- 단, 시스템 안전상 필요한 최소 내부 확인은 가능하되 이사님에게 중간 보고하지 않는다.
- 세션이 끊겨 큐 경계가 불명확해지면 추측으로 이어 붙이지 말고 다시 `큐시작`부터 요청한다.

## 4. `큐끝` 이후 출력 규칙

- 출력이 길면 한 메시지에 우겨 넣지 않는다.
- 산출물이 파일에 적합하면 파일로 만들고 Telegram 파일 전송을 우선한다.
- 텍스트로 답해야 하면 `1/3`, `2/3`처럼 나누어 보낸다.
- Telegram에서 Markdown 표는 읽기 어렵기 때문에 기본 출력에 표를 쓰지 않는다.
  - 대신 목록형, 번호형, 임시 웹, 이미지, 파일 중 적절한 형식을 사용한다.
- 설명 끝에는 ELI5 요약을 붙인다.

## 5. Git-first와 보존

- 큐 입력 원문 전체를 Git에 저장하지 않는다. 필요한 경우 sanitized 요약과 결정만 Git에 남긴다.
- 비밀키, 쿠키, 토큰, 세션 ID, 채팅방 ID, 개인 raw payload는 Git·메일·보고·후속 프롬프트에 남기지 않는다.
- 큐로 받은 요구가 코드·정책·일정 변경이면 기존 Git-first, Agent Mail, RELAY, Task Contract 규칙을
  그대로 따른다.
