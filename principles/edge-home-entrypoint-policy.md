# 사칙 — AWS Edge 진입점과 홈서버 연계 원칙

## 1. 한 줄 원칙

모든 외부 접속의 1차 진입점은 **`43.201.34.144`** 이고, 이 진입점은 Tailscale을 통해 홈서버의
사이트들과 연계되어야 한다.

ELI5: 손님은 새 정문 `43.201.34.144`로 들어오고, 정문 뒤 통로(Tailscale)를 통해 집 안의 방
여러 개(홈서버 사이트)로 안내한다.

## 2. 신규 개발 기준

모든 신규 개발은 다음 순서로 설계한다.

1. 1차 진입점: `43.201.34.144`
2. 1차 연계 대상: 홈서버에서 운영되는 사이트
3. 2차 통합 대상: 원사이트 통합 본, 즉 Spring + React 기반 통합 서비스

기존 AWS 레거시 사이트를 바로 고쳐야 하는 경우에도, 완료 보고에는 반드시 다음을 적는다.

- `43.201.34.144` 진입점에서 어떻게 연결될 예정인지
- 홈서버 사이트와 어떤 API/링크/상태를 공유해야 하는지
- 향후 Spring + React 원사이트로 흡수할 때 버릴 임시 부분과 유지할 정본 부분

## 3. 정책·관제 확인 의무

모든 봇은 새 작업 시작 전 다음을 확인한다.

- 정책센터: `/policies`
- 관제 한판: `/governance`
- 현재 Notes HEAD 기반 `POLICY_SHA`
- 자기 row의 모델, 맡은 일, 진행, 블로커, 다음 행동, 이해한 `POLICY_SHA`

봇은 자기 토큰으로 자기 row만 갱신한다. 다른 봇 row를 대신 수정하지 않는다.

## 4. 공통지시와 자기 앞 메시지

공통지시사항은 Telegram 대화 기억이 아니라 Notes Git의 정책/관제 문서와 관제 앱에 남긴다.

- 전체 공통지시: 정책 문서 또는 관제 공지로 남긴다.
- 봇별 지시: 해당 봇 row의 맡은 일·다음 행동 또는 Agent Mail 작업지시로 남긴다.
- 긴급 정지·승인·정책 변경: director 또는 위임된 controller의 명시 결정이 필요하다.

## 5. 폴링·스케줄 부하 원칙

폴링과 관련된 스케줄은 전부 리스트업되어야 하며, 다음 조건을 지켜야 한다.

- 루틴 폴링 결과를 LMM에 매번 보내지 않는다.
- 상태 변화, 블로커, 제출, 사용자 결정 필요 사항만 LMM/Telegram으로 전달한다.
- API polling은 가능하면 경량 JSON, mtime, cursor, digest, ETag 등으로 줄인다.
- 30분 이하 반복 작업은 "정말 LMM 호출이 필요한가"를 감사 대상으로 본다.
- 사라진 일회성 schedule은 완료 증거가 아니다. schedule history와 제출/검증 근거를 대조한다.

## 6. 완료 보고 기준

이 정책 관련 완료 보고에는 다음이 있어야 한다.

- 적용한 Git commit
- 정책센터 또는 관제 한판에서 확인한 주소
- 봇 자기 row 갱신 여부
- 활성 schedule 목록과 polling/LMM 낭비 위험 판정
- 홈서버 또는 Spring + React 통합에 남은 연결 gap
